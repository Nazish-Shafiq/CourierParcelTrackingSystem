# Authentication and Security

## Architecture

Authentication follows the existing Controller -> Service -> Repository structure:

- `Controllers/AuthenticationController.cs`
- `Services/AuthenticationService.cs` and `Services/Interfaces/IAuthenticationService.cs`
- `Repositories/AuthenticationRepository.cs` and `Repositories/Interfaces/IAuthenticationRepository.cs`
- `Extensions/DependencyInjectionExtensions.cs`
- `Extensions/JwtAuthenticationExtensions.cs`
- `Extensions/SwaggerExtensions.cs`
- `Setting/JwtSettings.cs`

The existing database-first entities and schema are retained. No migrations or new tables are required.

## Password security

`Users.PasswordHash` stores only the hash generated by ASP.NET Core `PasswordHasher<User>`.
Registration calls `HashPassword`; login calls `VerifyHashedPassword`. If the hasher reports
`SuccessRehashNeeded`, the stored hash is upgraded. The original password is never saved or
included in an API response.

The JWT signing secret is independent of all user password hashes. It is used only to sign
new JWTs and validate their signatures.

## Configure secrets

The project uses the existing `UserSecretsId` in its `.csproj`. From the API project directory:

```powershell
dotnet user-secrets set "JwtSettings:SecretKey" "<private-random-secret-at-least-32-bytes>"
dotnet user-secrets set "BootstrapAdmin:Key" "<separate-private-bootstrap-secret>"
```

Do not commit either secret to source control or share them. `appsettings.json` contains only
the non-secret JWT issuer, audience, and expiry settings.

## Roles and account creation

The implementation uses the role IDs already present in the database:

| RoleId | Role |
|---:|---|
| 1 | Admin |
| 2 | Booking Agent |
| 3 | Dispatcher |
| 4 | Courier |
| 5 | Customer Viewer |

- Bootstrap creates the first Admin only. It requires `BootstrapAdmin:Key` and is disabled once
  an active Admin exists.
- Admin can create Booking Agent, Dispatcher, or Courier accounts.
- Booking Agent can create Customer Viewer accounts.
- A customer registration creates the linked `User`, `UserRole`, and `Customer` records in
  one database transaction.
- Existing resource controllers require an authenticated JWT. Registration endpoints enforce
  their creator role.

## Endpoints

| Method | Endpoint | Access |
|---|---|---|
| POST | `/api/auth/bootstrap-admin` | Anonymous + one-time bootstrap key |
| POST | `/api/auth/login` | Anonymous |
| POST | `/api/auth/register-staff` | Admin |
| POST | `/api/auth/register-customer` | Booking Agent |
| GET | `/api/auth/me` | Authenticated |
| POST | `/api/auth/logout` | Authenticated |
| GET | `/api/users` and other resource APIs | Authenticated |

## Swagger test sequence

1. Create the first Admin with `/api/auth/bootstrap-admin`.
2. Sign in using `/api/auth/login`.
3. Copy `data.token` from the response.
4. Click Swagger's **Authorize** button and paste the token (without adding `Bearer `; Swagger
   supplies the scheme).
5. Call `/api/auth/me` and a protected resource endpoint.
6. As Admin, call `/api/auth/register-staff` with `roleId` 2, 3, or 4.
7. Log in as the Booking Agent and use `/api/auth/register-customer`.
8. Try the staff/customer registration endpoints with the wrong role and verify a `403`.
9. Call a protected endpoint without a token and verify a `401`.
10. Test invalid login credentials and verify a `401`.

## Logout behavior

JWT access tokens are stateless. `/api/auth/logout` confirms the client logout action, but
cannot invalidate a copied token on the server. The frontend must delete its stored token.
Immediate server-side revocation would require a token denylist or another revocation store,
which is intentionally not added because the database schema is being kept unchanged.

## Build and run

```powershell
dotnet restore
dotnet build
dotnet run
```

The API must be run with the existing SQL Server database available. This packaging environment
does not have the .NET SDK, so a local `dotnet build` and live SQL/Swagger test must be performed
in Visual Studio or on the user's development machine.
